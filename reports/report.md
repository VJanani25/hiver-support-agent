# Hiver SDE Intern Assignment

## 1. Executive summary

This repository implements a conservative customer-support agent around three inspectable components: intent classification, retrieval of similar resolved conversations, and an escalation policy. The default code path runs on a small demo fixture so a reviewer can inspect the behavior without downloading the full Kaggle export.

No benchmark number is claimed yet. The real dataset and a human-reviewed golden set are intentionally required before reporting headline results.

## 2. Problem framing

Good support for one brand means the response is relevant to the customer's issue, grounded in how that brand historically handled similar messages, and cautious when the system lacks evidence. The project deliberately does not promise autonomous policy decisions, refunds, credits, timelines, or guarantees that are not present in retrieved support responses.

## 3. Data

The intended source is Customer Support on Twitter by thoughtvector on Kaggle. The preparation pipeline inspects the export before brand selection, pairs inbound customer tweets with linked support responses, and derives a small issue taxonomy from recurring language.

The checked-in fixture is synthetic/demo-only and exists for software validation. It is not a substitute for the dataset and is not suitable for a recruiter-facing result table.

## 4. Intent taxonomy

The starter taxonomy contains account access, billing/payment, refund/cancellation, delivery status, technical issue, product information, complaint, and other/unknown. The real run should review these categories against the selected brand's actual conversations and merge or split them when the data supports doing so.

## 5. System architecture

1. Normalize and tokenize the customer message.
2. Predict intent with a deterministic TF-IDF + multiclass logistic regression model.
3. Retrieve the top historical customer/support pairs using sparse TF-IDF cosine similarity.
4. Draft a reply by reusing the strongest retrieved support response.
5. Escalate if the request is high-risk, ambiguous, low-confidence, or lacks evidence.

## 6. Evaluation methodology

The harness computes accuracy, macro F1, weighted F1, per-class precision/recall/F1, and a confusion matrix. Reply checks measure whether the generated response has lexical support in retrieved evidence. The judge output is labelled as a deterministic grounding check, not an LLM-as-judge result.

The candidate golden-set builder creates 200 rows with model suggestions but leaves the true label fields blank. A human must review and fill those fields before any benchmark is reported. A future LLM judge should be compared with a human-rated subset using exact agreement, within-one agreement, and correlation, with limitations documented.

## 7. Results

Results are generated by `scripts/run_baselines.py` and `scripts/evaluate.py`. The checked-in fixture is a smoke test only, so no accuracy, F1, reply-quality, or escalation-quality number is presented here as a result.

## 8. LLM-as-judge validation

Not run in this repository. The next implementation step is to add a provider-backed structured rubric with groundedness, correctness, relevance, completeness, helpfulness, tone, hallucination, overall score, and reason. A human-rated subset must be scored first or in parallel; judge agreement must be reported with limitations.

## 9. Failure analysis

The real run should populate five rows from actual evaluation examples:

1. **Ambiguous issue:** two intents share the same language; inspect the retrieved context and add disambiguating features.
2. **Weak retrieval:** the message has no close historical neighbor; lower-confidence cases should escalate.
3. **Inconsistent historical replies:** similar issues were resolved with different wording; review the brand's support policy.
4. **Over-escalation:** common intent has low confidence because the taxonomy is too fine-grained; merge only with evidence.
5. **Inappropriate auto-handling:** a sensitive message passed the generic threshold; expand risk terms and test adversarial cases.

These are failure-analysis categories, not fabricated observed examples. The evaluation output should replace them with real rows.

## 10. What is misleading about my headline number?

The strongest headline metric can still mislead. Conversation samples are correlated, class imbalance can make accuracy look good, and retrieval can leak near-duplicate turns across splits. A small golden set carries label uncertainty. Lexical grounding checks do not establish policy correctness, and an LLM judge can reward fluent but unsupported answers. The real report should use grouped or time-aware splits, macro F1, per-intent results, and human review rather than one number.

## 12. Decision log

1. **One brand at a time.** It keeps support language and policy evidence coherent.
2. **Inspect before choosing a brand.** The dataset's actual volume and link quality should drive the choice.
3. **Pair linked turns.** A support response is evidence only when connected to a customer message.
4. **Use eight starter intents.** They are broad enough for a first run and include an explicit unknown class.
5. **Use TF-IDF + logistic regression.** It is reproducible, interpretable, and easy to explain.
6. **Use retrieval evidence.** The reply can be traced to historical support behavior.
7. **Reuse the top support response.** This reduces unsupported policy invention in demo mode.
8. **Escalate conservatively.** Low confidence and missing evidence are safety signals, not failures to hide.
9. **Keep suggestions separate from labels.** Model predictions cannot silently become ground truth.
10. **Use deterministic seeds.** Reviewers should get the same sample and candidate set.
11. **Report macro F1.** A majority class should not dominate the evaluation story.
12. **Do not claim an LLM judge without validation.** Agreement with human ratings is part of the deliverable.
